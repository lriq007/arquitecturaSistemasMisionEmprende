- (decision) AD-1 — Dependencias entre módulos de dominio: Las fases pueden compartir información mediante contratos explícitos (interfaces TypeScript), pero ningún módulo puede importar directamente el repositorio.ts de otro módulo. Los contratos compartidos (p.ej. RepositorioResultadoLego) se definen en compartido/ o en una capa de aplicación neutral; una implementación DynamoDB separada los cumple. Binds: todos los módulos de fase (fase1..faseN). Prevents: acoplamiento a detalles de persistencia internos de otra fase; dos fases evolucionando la misma interfaz DynamoDB incompatiblemente.
- (decision) AD-2 — Máquina de estados del juego: Vive en compartido/maquinaEstados.ts como módulo compartido del dominio global. Exporta: (a) el array tipado FASES_ORDEN, (b) el mapa TIEMPOS_POR_FASE, (c) las constantes de cada string de fase. El módulo shared no importa de ningún módulo funcional (acíclico). profesor y todas las fases importan de aquí; nadie duplica los strings. Binds: profesor, fase1..faseN, cualquier Lambda de orquestación futura. Prevents: strings de fase hardcodeados por fase, lógica de transición duplicada, ciclos de importación.
- (decision) AD-3 — Identidad del profesor en el token: Todo token de profesor (Cognito o JWT interno) debe incluir un profesorId estable. El backend extrae ese profesorId del token en cada request y lo usa como condición obligatoria en todas las queries de sesiones (nunca lo acepta del body o query string). Implementación actual (token sin profesorId + contraseña compartida) es deuda técnica explícita: FR-005 no está efectivamente implementado hasta que el token lleve identidad. Binds: profesor/seguridad.ts, todas las rutas de sesiones del profesor. Prevents: un profesor con token válido acceda a sesiones de otro profesor; aislamiento por oscuridad en lugar de por diseño.
- (assumption) Deuda técnica registrada: FR-005 (aislamiento entre profesores) requiere que el token lleve profesorId. El equipo debe decidir si esto entra al sprint actual antes de la entrega final.
- (decision) AD-4 — Rankings sincrónicos, EventBridge diferido: El cálculo de ranking se realiza de forma síncrona en endpoints dedicados dentro de cada módulo de fase (/api/faseN/ranking). No se usa EventBridge para la propagación de rankings. FR-018 (publicar transiciones a EventBridge) y FR-051 (ranking async) quedan diferidos. Binds: fase1..faseN. Prevents: introducir Lambda asíncrona de ranking o bus de eventos sin acuerdo explícito del equipo.
- (decision) AD-5 [ADOPTED] — Dirección de dependencias hacia el núcleo: api.ts conoce a servicio.ts; servicio.ts conoce la interfaz del repositorio; repositorio.ts concreto no conoce al servicio. El núcleo no importa AWS SDK directamente. Confirmado en todo el código existente.
- (decision) AD-6 [ADOPTED] — Tabla DynamoDB única con GSI: Una tabla por entorno (MisionEmprende-{env}), PK+SK, GSI1 para búsquedas secundarias. Prefijos de clave (SESION#, GRUPO#, CODIGO#) solo en repositorio.ts. Confirmado en template.yaml y todo repositorio existente.
- (decision) AD-7 [ADOPTED] — Autenticación via helpers compartidos: grupos usan contextoDesdeEvento(), profesores usan validarProfesorDesdeEvento(). Ningún api.ts parsea tokens manualmente.
- (constraint) Módulos planificados no implementados: fase4 (Pitch y Evaluación Cruzada) y catalogo (admin). Deben seguir AD-1..AD-7. Su ausencia es de implementación, no de diseño.
